# 馒头斗嘴设计

日期：2026-11-05

## 目标

新增一个群内活动「馒头斗嘴」：馒头从群聊记忆里挑一个和群友说过的话有关的题目，@ 触发消息的群友当对手；其他群友在 60 秒内押注谁赢；押注截止后，馒头和对手打满 5 个回合，由馒头（模型）判定输赢，再按押注结算好感度。

这个功能是 `nonebot-plugin-group-chat-memory` 的软联动：出题、每回合回嘴和最终判定都复用该插件已经配置好的聊天模型。群聊记忆插件不可用或没有配置模型时，整个功能自动关闭，不触发、不占活动席位，也不出现在强制事件列表里。

## 已确认的用户规则

- **触发**：普通群消息按概率触发；默认 0.05%。SUPERUSER 可以用 `/馒头斗嘴概率` 查看或修改，运行时覆盖持久保存。`/馒头强制事件` 新增第 9 项「馒头斗嘴」。
- **对手**：触发这条消息的人。馒头 @ 他，他在 5 个回合里回嘴；其他群友押注。
- **出题**：题目必须和群友说过的话有关，由群聊记忆插件提供上下文、馒头生成。题目在押注开始前就展示，让押注的人知道在赌什么。
- **押注窗口**：60 秒。先押注，截止后再开始斗嘴。
- **押注选项**：6 个编号，押「群友赢」1/3/5 点、押「群友输（馒头赢）」1/3/5 点。每人只能押一次；好感不足所选点数不能押，被拒绝后可以改选更低的档位。被 @ 的当事人不能押注。
- **没人押注**：照常斗嘴，只结算当事人的 ±3/-5。
- **斗嘴**：5 个回合，每回合 = 对手说一句 + 馒头接一句。每回合给对手 60 秒；超时视为弃权，直接判对手输并结算，不再等满 5 回合。
- **判定**：5 回合打满后由匿名 A/B 中立裁判评分并判断输赢；结算消息附上评分和一句点评（为什么赢/为什么输）。
- **立场**：出题时同时给出群友和馒头互相矛盾的两方立场；斗嘴期间双方都不得改立场，馒头不能附和、认输或替对方说话。
- **当事人结算**：赢 +3，输（含超时）-5。这笔是额外结算，不参与押注奖池。
- **押注结算**：赢家先拿回自己的本金，再按各自押注额的比例分配输家的押注；除不尽的余数按押注额从大到小分配，押注额相同则给最早押注的赢家。赢的一方没人押时，所有押注原路退回，只结算当事人的 ±3/-5。
- **降级**：群聊记忆插件未加载、未配置聊天模型、或模型调用失败时，活动取消，所有押注原路退回，不结算 ±3/-5。

## 非目标

- 不做独立的模型配置；只复用群聊记忆插件的聊天客户端。
- 不做复杂平局判定；模型评分相同时按平局掷骰判定，无法解析时取消并退款。
- 不做押注的持久化；活动状态只存在内存里，机器人重启会丢失（与现有转盘参与费的行为一致）。
- 不改变现有活动、押注、好感度上限和新手保护的语义。
- 不做群聊记忆插件的数据迁移或清空；只读取它已有的最近消息和长期记忆。

## 约束

- Python `>=3.9,<4.0`，不新增依赖。
- 所有群友可见文案为中文；需要指向具体人时沿用「@ + 空格 + 正文」，斗嘴的每句馒头回应改用「回复（引用）+ 空格 + 正文」。
- `poetry run pytest -q` 全绿，`poetry run ruff check .` 无告警。
- 群聊记忆插件是软依赖：未安装、未加载或版本不含所需接口时，本功能必须安全关闭。
- 活动从开场到结算通常 1–2 分钟；极端情况约 `60 + 5 × (60 + 20) + 20 + 20` 秒（约 8 分钟），期间占用本群的活动席位。

## 方案

### 选定：新模块 `bicker.py` + 复用记忆插件的聊天客户端

新增 `BickerCoordinator`，自己管理押注状态、5 回合对话、超时和结算；通过一个薄的 `GroupMemoryAdapter` 调用群聊记忆插件已暴露的对象：

- `store.recent_messages(group_id, limit)`：最近群消息，用于出题和冷群判断。
- `chat_client.complete(ChatContext(), text)`：调用该插件配置好的 OpenAI 兼容模型；空的 `ChatContext` 由适配层自己构造，协调器不导入记忆插件的模型类。

不使用 `context_builder.build()`：它会在出题前多做一次 Embedding 查询（默认 3 秒超时），而题目只需要最近的群聊内容；跳过它同时减少一个失败点。适配层用 `get_plugin("nonebot_plugin_group_chat_memory")` 懒加载，不硬导入；测试时注入 Fake。

被否掉的方案：

- **扩展现有 `bet.py`**：博弈是数字排列竞猜，状态机是「三人作答 + 相似度」，和「押注 + 5 回合对话 + 模型判定」几乎没有可复用的部分，硬塞进去会让两套流程互相拖累。
- **直接写在 `ambient.py`**：`ambient.py` 已经负责按顺序掷骰和路由，再加押注状态、每回合超时和模型调用会让它更难测试。
- **自己直连 OpenAI 接口**：控制力更强，但要把群聊记忆插件的运行时配置、重试、超时逻辑复制一遍，容易和上游脱节。

## 流程

### 1. 触发

- 群消息路径：`ambient.py` 在找字、博弈、桃子问答、群友问答、转盘之后、小动作之前，按 `mantou_affection_bicker_chance`（默认 0.0005）独立掷一次。
- 前置条件：群聊记忆插件可用、聊天模型已配置、本群没有其它待结算活动、触发者不是机器人自己。
- 不设好感度门槛；好感 0 的群友也可以被 @。
- 强制事件路径：`/馒头强制事件` 第 9 项直接开局，绕过概率，但保留群席位和记忆插件可用性检查。

### 2. 出题

先读 `store.recent_messages(group_id, 30)`。列表为空（新群或记忆刚清空）时直接取消，不触发——避免模型凭空编一个和群聊无关的题目。

把最近消息压成「昵称: 文本」的短列表，和下面的指令一起作为 `current_text` 发给模型（`ChatContext()` 为空）：

```
下面是本群最近的聊天记录：
{最近消息}

请根据这些内容，出一道适合群友和馒头正反辩论的题目，并给出正反两方的立场。
要求：题目必须和群友说过的话有关；两方立场必须互相矛盾，不能是同一意思的两种说法；每条不超过 30 字；不要解释，不要加引号。
只输出 JSON：{"topic": "辩题", "group_side": "群友立场", "bot_side": "馒头立场"}
```

题目和两方立场必须一起产出，否则馒头没有可守的立场，只能顺着对方上一句接话，斗嘴会退化成闲聊。

解析规则：

- 优先解析 JSON 的 `topic` / `group_side` / `bot_side`，各自取第一行、去掉首尾引号，立场截断到 40 字。
- 模型只回了一句普通文本（没按 JSON 返回）时，题目取第一行，立场兜底为「支持「题目」」和「反对「题目」」。
- 两方立场缺失或完全相同，同样用兜底立场，避免双方立场一致导致无法辩论。
- 题目为空、超时或模型失败：取消活动，不发任何群消息（只记日志）。
- 题目是群级别的，不要求一定引用被 @ 的当事人自己的发言。

### 3. 开场与押注

开场消息 @ 当事人，列出题目、押注选项和规则：

```
@群友 🎤 馒头斗嘴！
题目：{题目}
群友立场：{群友立场}
馒头立场：{馒头立场}
60 秒内可以押注，回复编号，每人一次：
1. 押群友赢 1 点
2. 押群友赢 3 点
3. 押群友赢 5 点
4. 押群友输 1 点
5. 押群友输 3 点
6. 押群友输 5 点
好感不足所选点数不能押；当事人不能押注；没人押注也照常斗嘴。
```

- 押注在收到编号时立刻扣除对应好感度，并记录实际扣除值。
- 当事人回复 1–6 会被提示「你是当事人，不能押注」，不扣好感。
- 其他人重复押注会被提示「你已经押过了」，不重复扣。
- 好感不足所选档位：提示「好感不足 X 点，可以改选更低的档位」，不扣好感，仍可继续押。
- 押注窗口 60 秒（`mantou_affection_bicker_bet_window`）。到点关闭押注，发一条汇总：

```
押注截止：3 人参与，押注总额 9 点。
```

没人押注时发：

```
没人押注，馒头直接开斗。
```

### 4. 斗嘴

- 押注截止后，馒头 @ 当事人并说明双方各自的立场：

```
@群友 题目：{题目}
你的立场：{群友立场}
我的立场：{馒头立场}
来，说说你的看法。请在 60 秒内回嘴。
```

- 每回合：当事人发一条文本消息 → 记录为这一回合的回嘴 → 调用模型生成馒头的一句回应 → 以回复（引用）当事人这条消息的形式发出 → 进入下一回合。
  用回复而不是直接发，是因为群里同时可能有人聊天，不引用的话分不清哪句是斗嘴的回应。
- 5 个回合 = 当事人 5 次回嘴 + 馒头 5 次回应。第 5 次馒头回应发出后进入判定。
- 每回合给当事人 60 秒（`mantou_affection_bicker_round_timeout`）。超时立即判当事人输并结算。
- 只有当事人的文本消息算回嘴；其他人发言、图片、表情、空文本都忽略。同一回合内当事人发多条，只取第一条，等馒头回应后才进入下一回合。
- 馒头的每句回应要求不超过 60 字，只输出一句话，不加解释和引号；超长截断到 60 字。
- 每回合的回应 prompt 固定带上「你是馒头 / 你的立场 / 对方立场」和辩论规则：立场从头到尾不能变，先戳破对方上一句的具体说法再拉回自己的立场，禁止「你说得对」「有道理」「我同意」「我服了」这类附和或认输，禁止重复自己说过的理由。这是让斗嘴保持正反辩论而不是顺着对方接话的关键。
- 如果馒头这一句仍然命中认输句式（`你说得对`、`你说服我了`、`我同意`、`我服了` 等），追加一句提醒重写一次；重写仍命中时保留原文，交给裁判在「立场一致性」上扣分。

### 5. 判定

把辩题、双方立场和 10 句对话匿名成 A/B 后交给模型：

```
你是一个完全中立的斗嘴裁判，不代表 A 或 B。
辩题：...
A 的立场：...
B 的立场：...

A: ...
B: ...

只看辩论表现评分（0-10 分）：
- 立场一致性：有没有始终为自己那一方辩护，有没有反过来赞同对方、改口或中立；
- 反驳质量：有没有正面拆掉对方上一句的具体说法；
- 论据与机智：理由、例子、类比、反问是否有说服力；
- 切题：有没有跑题或重复自己。
不要评判哪一方的立场更正确，也不要因为某一方更长或更像机器人就偏袒。
reason 要指出决定胜负的具体回合和原因，说明谁在哪一句守住了或丢了立场。
只输出 JSON：{"a_score": 0, "b_score": 0, "winner": "A", "reason": "一句话说明胜负原因"}
```

A/B 的立场按本轮匿名映射填：群友分到 A 时 `A 的立场` 是群友立场、`B 的立场` 是馒头立场，反之对调。

解析规则：

- 优先解析 JSON；`winner` 为 A/B 时按本轮随机映射还原成群友/馒头。
- 没有 `winner` 但有分数时按高分者判定；分数相同按平局掷骰判定。
- 兼容旧的「群友赢」/「馒头赢」纯文本回复。
- 两者都没有、同时出现、或模型调用失败 → 判定失败：取消活动，所有押注原路退回，不结算 ±3/-5。
- 结算消息附上「裁判点评（评分：群友 X / 馒头 Y）：理由」，让群友知道为什么赢/输。

### 模型调用与超时

所有模型调用都走适配层的 `complete(text)`，`ChatContext` 为空，完整对话放在 `current_text` 里；这样每回合都看得到题目和已经打过的全部内容，也不会把群里的无关消息混进来。

- 出题：1 次，见上节。
- 每回合馒头回应：1 次，输入是辩题 + 双方立场 + 已有 transcript + 对手这一句，指令是「守住你的立场、反驳对方上一句，只输出馒头接下来的一句回嘴，不超过 60 字」；命中认输句式时多 1 次重写。
- 判定：1 次，输入是辩题 + 匿名后的双方立场 + 完整 transcript，指令见上节。

一局共 7 次模型调用，最多 8 次（出现一次认输重写）。每次调用外面套 `asyncio.wait_for(..., timeout=20)`；超时按模型失败处理（取消 + 退款）。记忆插件自己的 `ChatClient` 还有重试，外层超时会直接取消这次等待，不会让一局卡到它的 60 秒 × 3 次重试。

transcript 里每句最多 200 字（对手）或 60 字（馒头），5 回合总计远低于记忆插件 6000 字的上下文预算。

### 6. 结算

- 当事人：赢 +3，输 -5。走 `service.adjust`，受 0 和上限约束，显示实际生效值。
- 押注者：
  - 赢家拿回本金（实际扣除值），再按各自押注额的比例分配输家的实际押注总额。
  - 除不尽的余数按押注额从大到小分配，押注额相同则给最早押注的赢家（按押注时间排序）。
  - 赢的一方没人押：所有押注者原路退回本金，只结算当事人的 ±3/-5。
  - 奖池为 0（没有输家）：赢家只拿回本金。
- 所有加减都走 `service.adjust`，不受每日获取总上限和联动冷却限制。
- 结算消息先写当事人的 ±3/-5 和裁判点评，再逐人 @ 一行写押注结果、实际变化和当前好感。

## 状态与数据结构

```python
BICKER_STAKES = (1, 3, 5)
BICKER_OPTIONS = {
    "1": (True, 1), "2": (True, 3), "3": (True, 5),   # True = 押群友赢
    "4": (False, 1), "5": (False, 3), "6": (False, 5), # False = 押群友输
}
BICKER_ROUNDS = 5
```

`PendingBicker` 保存：

- `group_id`、`trigger_id`、`trigger_name`
- `topic`、`group_side`、`bot_side`、`send`
- `phase`：`preparing` / `betting` / `debating` / `judging` / `settled`
- `bets: dict[user_id, Bet]`，`Bet` 保存 `side`（押群友赢/输）、`stake`、`actual`、`nickname`、`placed_at`
- `transcript: list[tuple[str, str]]`（角色 + 文本）
- `round`：当前回合 0–5
- `accepting`、`awaiting_reply`（馒头正在生成回应时不再收这一回合的第二条消息）
- `bet_task`、`round_task`：分别管理押注截止和每回合超时

## 命令与集成

- `/馒头斗嘴概率 [0.05%]`：SUPERUSER 查看或修改触发概率，持久保存。
- `/馒头强制事件` 第 9 项「馒头斗嘴」：绕过概率，保留群席位和记忆可用性检查。
- `ambient.py`：
  - 新增 `bicker` 参数并 `attach_bicker`，让 `EventCoordinator.busy()` 覆盖斗嘴。
  - 在群消息判定链中转盘之后、小动作之前调用 `service.bicker_triggered()` / `bicker.start()`。
  - 在 `handle_ambient` 开头检查 `bicker.is_debater_turn(group_id, user_id)`：命中就把这条消息交给 `bicker.handle_debate()` 并 `return`，不再掷其它活动。ambient matcher 仍是 `block=False`，不会吞掉命令和其他插件。
  - 现有答案 matcher 增加 `bicker.answer()`，处理押注编号。
- `force.py`：新增 `FORCE_ACTIVITY_BICKER = "bicker"`、编号 9 和对应文案；分发直接调用 `bicker.start(...)`，概率判定只发生在 ambient 路径。
- `__init__.py`：组装 `GroupMemoryAdapter` 和 `BickerCoordinator`，注入 `EventCoordinator`；对外不新增 API。
- `config.py`：新增三个配置字段。
- `README.md`：新增「馒头斗嘴」章节、配置项、命令表、强制事件第 9 项。
- `pyproject.toml`：版本号按发布流程递增。

## 失败与边界

| 情况 | 处理 |
|---|---|
| 群聊记忆插件未加载 | 不触发；强制事件提示「群聊记忆插件不可用」。 |
| 聊天模型未配置 | 出题前失败，取消，不发群消息。 |
| 出题失败 / 题目为空 | 取消，不发群消息。 |
| 押注阶段发送失败 | 记录日志，活动继续；押注者仍按已记录状态结算。 |
| 馒头某回合回应失败 | 取消，所有押注原路退回，不结算 ±3/-5，发一句道歉。 |
| 判定失败 | 同上。 |
| 当事人回合超时 | 判当事人输，正常结算押注和 -5。 |
| 当事人在押注阶段离开 / 不说话 | 押注照常；斗嘴回合超时判输。 |
| 押注者好感在结算前被其它操作扣光 | 押注已在押注时扣除，奖池固定为实际扣除总额；后续好感变化不影响本次结算。 |
| 机器人重启 | 活动丢失；已扣的押注不退（与现有转盘参与费一致）。 |

## 留给实现的决定

- 押注在押注时立刻扣除，而不是结算时扣除；这样“额度不够不能参与”的判定和奖池金额一致。代价是机器人重启会丢失未结算的押注（与转盘参与费一致）。
- 押注本金不享受新手保护：押注是自愿选择，必须拥有所选点数；当事人的 -5 走正常新手保护。
- 押注本金按实际扣除值记录；奖池在押注截止时固定，后续好感变化不影响本次结算。
- 余数给最早押注的赢家，沿用 `bet.py` 的「最早提交者拿余数」口径。
- 馒头每回合的回应、题目和判定都复用群聊记忆插件的系统人格；不额外拼接新的系统提示词，只把指令放进当前消息。
- 斗嘴期间不消耗群聊记忆插件的每小时请求额度；触发概率本身已经很低，避免再和它的随机回复抢额度。
- 当事人回嘴只接受纯文本，长度截断到 200 字；非文本消息忽略，不重置 60 秒计时。
- 活动期间占用群席位，极端情况最长约 8 分钟；这是为了让押注和 5 回合对话不被其它活动打断。
